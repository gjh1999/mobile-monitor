# 轻量级 Agent 调度 CLI：架构设计

**状态：架构草案，待项目负责人评审；尚未开发。** 2026-11-28。本文是[已确认需求](AGENT_CLI.md)的技术方案，部署和运行命令均为设计示例，不是现版操作说明。[开发计划](AGENT_CLI_PLAN.md) · [项目主文档](跨设备开发工作台方案.html#agent-cli)

## 1. 边界与原则

- 本机 Rust 核心负责任务状态、工单事件、模型适配、权限、执行、用量与报告；终端是首个交互入口。沿用项目现有 R51 的项目身份、人工优先和审批语义；重构中的 Rust 本机核心可复用模块，但新 CLI 不依赖尚未交付的 Go 协调服务。
- 一个项目对应一个受控代码根目录和独立数据分区。目标、工单、Agent 配置、预算、审批规则及日志都带不可缺省的 `project_id`。跨项目通信只允许用户显式发起的摘要引用，不能透传文件路径、原文或执行权限。
- 工单是所有动作和 Agent 交流的事实来源。调度器只能消费已持久化的工单事件；状态面板和报告都由同一事件投影生成。不能先执行、后补单。
- Codex 主控负责计划、派工、普通复核和最终汇总；DeepSeek Flash 执行常规工单；Codex Astra 处理升级工单与重点复核。名称是角色配置，不绑定固定供应商接口或未经核实的模型 ID。
- 首版是单机、单项目内串行执行。同机可以登记多个项目，但调度器不会在同一项目并行写代码。跨设备自动派工、同项目多执行者合并、自动发布留到后续阶段。

## 2. 组件与数据流

```text
用户 ── CLI/TUI（聊天、工单、状态、设置、审批）
                    │ 本机 IPC / 嵌入式命令接口
                    ▼
             Rust 调度核心
       ┌────────┼────────┬──────────┐
       ▼        ▼        ▼          ▼
   工单事件库  目标调度  审批/隔离    报告/用量
       │        │        │          │
       └────────┴────┬───┴──────────┘
                     ▼
          Agent 适配器（主控 / Flash / Astra）
                     │
             项目受控工具与工作区
```

建议目录为 `refactor/agent-cli/`，内含 Rust workspace：`lanxi-agent-core`（领域与状态机）、`lanxi-agent-store`（SQLite）、`lanxi-agent-adapters`（模型协议）、`lanxi-agent-runtime`（工具与隔离）、`lanxi-agent-cli`（命令与 TUI）。这是仓库布局方案，实际建目录时以现有重构布局为准。核心库接口独立于终端渲染，后续桌面界面可读同一状态投影。

### 2.1 Rust 核心职责

| 模块 | 输入 | 输出与约束 |
|---|---|---|
| 项目注册 | 项目路径、项目身份、设置 | 规范化根目录、控制权状态、独立配置；拒绝重叠项目根目录 |
| 工单存储 | 用户/Agent 消息、动作请求、工具回执 | 事务写入带序号的事件、当前投影、幂等键；日志可追溯 |
| 目标调度 | 目标、验收项、预算、工单状态 | 确定下一工单、选角色、预留调用；暂停/恢复/完成须有证据 |
| 适配器 | 已批准的任务上下文 | 统一消息、工具请求、用量、限额、错误与取消事件 |
| 权限执行 | 项目身份、规则版本、操作详情 | 路径校验、审批决定、受控工具执行和结果回执 |
| 报告器 | 工单事件与用量投影 | 定时摘要、审批/限额即时提示、去重和投递状态 |

现版 `universal_rpc.py` 的 Codex App Server 通信与 `task_control.py` 的持久意图是行为参考，Rust 不能直接把 Python 的状态库当作新库。接口兼容性、原线程复用及桌面共用控制权在集成阶段单独验证。[现有架构](ARCHITECTURE.md) · [项目控制](PROJECT_CONTROL.md)

## 3. 工单模型和事件协议

每个目标建立父工单；可执行任务、复核和审批可成为子工单。Agent 之间的消息必须指定同一项目下的 `ticket_id`，可引用父子工单；拒绝裸消息直接触发工具。用户的普通问答可保留聊天记录，凡改变目标、设置或执行动作的输入，先生成工单事件。

核心实体：`projects`、`goals`、`tickets`、`ticket_events`、`agent_profiles`、`approval_policies`、`tool_attempts`、`model_calls`、`usage_ledger`、`reports`。每张业务表带 `project_id`；SQLite 外键和写事务保证关系一致，读取时还要按项目授权过滤。日志正文与密钥分离，密钥走系统凭据存储或环境注入，不进入事件正文。

工单事件建议统一字段：`event_id`、`project_id`、`goal_id`、`ticket_id`、`seq`、`actor`、`kind`、`created_at`、`payload_ref`、`correlation_id`、`idempotency_key`、`policy_version`。事件只追加；状态由事件重放/投影得到。对更正和撤回写新事件，保留原始记录。长文本和工具输出可放项目隔离的内容存储，以哈希引用；默认在 CLI 显示可读摘要，展开可查原文或脱敏版本。

状态流：`待派发 → 执行中 → 待复核 → 已完成`；另有 `需返工`、`待审批`、`额度受限`、`已暂停`、`失败`。每次转移标明触发事件和操作者。工具调用先写 `requested` 与执行预留，再执行并写 `succeeded/failed/unknown`；崩溃后的 `unknown` 不自动重放，必须核对工作区和原生调用回执。周期报告只读投影，不推动状态。

## 4. 对话、Agent 设置与路由

CLI 提供聊天输入、工单列表/详情、三 Agent 状态和设置页。建议命令语义：`lanxi agent` 打开 TUI，`lanxi agent ticket <id>` 看时间线，`lanxi agent config` 修改项目内角色配置，`lanxi agent goal` 管理目标；具体命令名在实现时定稿。TUI 进度以验收项完成数和当前状态呈现，不展示没有依据的百分比。

每个角色设置 `adapter`、`model_id`、可支持的推理参数、权限档位、并发上限、调用/目标预算和超时。适配器在启动时公布能力集；CLI 对不可用参数显示“不支持”。配置修改生成 `config_changed` 工单事件及版本号；运行中的调用沿用启动时快照，新调用使用新版本。凭据不导出到工单。

主控按工单类型和明确的升级规则派给 Flash 或 Astra。建议首版规则：已定义验收且风险较低的实现交 Flash；跨模块设计、反复失败、影响审批/隔离/数据迁移的工单交 Astra；所有最终结论由主控核对证据。模型只能建议升级，Rust 核心根据配置规则执行或等待用户确认。重试、升级和人工接管都成为工单事件。

## 5. 项目隔离、工具和审批

`cwd` 或提示词无法限制任意子进程访问别的项目。首版区分两类能力：

1. **受控文件工具。** Rust 核心对每次读写重新解析路径、检查符号链接/重解析点和最终目标仍在登记的项目根目录内；写入使用受控句柄及原子替换。拒绝绝对路径、`..`、跨项目引用与超出策略的文件。测试覆盖检查到使用之间的路径变化。
2. **命令执行。** 只有验证过的操作系统沙箱或隔离执行环境，能限制实际文件与进程访问时，才允许模型自主运行任意项目命令。没有该能力时，命令保持待人工审批或在受控的有限工具中完成；不能把路径检查包装成命令级隔离。Windows 试点需验证沙箱进程身份、文件 ACL/映射、网络与子进程继承；失败则禁用自主命令执行。

自动审批以项目内规则为准，建议默认关闭，由用户显式开启。规则绑定项目、工具类别、规范化命令或文件范围、工作目录、有效期和版本；每次请求比对完整详情、当前项目写入权、目标状态、预算和规则版本。命中后写 `approval_decided(auto)`、规则 ID 与实际操作摘要，再执行；缺详情、跨根目录、规则不匹配或控制权失效都转待人工。人工决定也只作用于当前请求 ID，不能批量隐式扩大权限。现版 R51 和重构方案的审批语义仍是外部 Codex 连接的边界，新 CLI 不代替其原生审批。

项目隔离验收至少覆盖：A 的 Agent 不能读写 B 的代码、不能调用 B 的密钥或规则、不能在 B 的工单发消息；目录别名、符号链接、大小写与路径竞态也要测。项目切换时停止当前派工并切换数据库视图，不能把 A 的上下文带入 B。

## 6. 目标模式、用量和报告

目标记录描述、验收项、范围、暂停状态、时间/调用/token 预算与版本。主控只能在满足验收证据、无未决审批和无不确定动作时提议完成；用户可暂停、恢复、修改或结束。修改目标产生新版本，旧派工先停下核对。与 Codex 原生 goal 的映射待接口核验；首版可由 Rust 自己持有目标状态，不声称已同步原生 goal。

每个模型调用以稳定 `call_id` 记录角色、工单、模型、开始/结束、结果与原始用量来源。`usage_ledger` 按返回的输入、输出、缓存等字段记录；总量只在字段语义明确时计算。缺失字段显示“未知”，不能把零当未知，也不能将估算混入实测。聚合以 `call_id + usage_revision` 去重，提供 Agent、工单、目标和项目维度。额度受限要记录适配器原始错误、可用的刷新时间及等待策略；没有确认恢复前不继续自动调用。

报告器按项目配置周期生成快照：目标、完成/进行/阻塞工单、Agent 状态、待审批、额度、token 实测覆盖范围和下一步。审批出现、额度受限、预算即将用尽、执行结果未知时立即生成事件报告。报告写入本地持久队列，终端在线时直接提示；外部通知渠道后续另行接入。用户可查看上次和下次报告时间，重启后不重复发送已回执报告。周期和免打扰默认值在试点时确定。

## 7. 恢复、日志与集成

- SQLite 使用迁移版本和事务；进程重启重放事件、重建投影，校验预留与实际适配器状态。发送结果未知保留待核对，不自动二次派工。
- 审计日志记录项目、工单、操作者、动作、决定、用量来源和错误；按事件 ID 关联原始调用。日志展示脱敏，原始模型消息是否保留及保留期限按项目配置。支持导出单工单的可复核记录。
- CLI 启动时检查项目是否被现版澜汐、IDE 或外部 CLI 占用。取得项目写入权后才能派工、批准和落盘；只读查看不需要写入权。试点先使用独立测试项目和数据目录，不修改 R51 生产库。与未来 Rust 重构核心整合时保留同一控制权语义。
