# 澜汐（LANXI）实时工作区与 Codex 会话同步技术架构设计

**版本：** V1.0  
**架构定位：** 跨设备开发工作连续性系统  
**核心目标：** 让多台电脑像一台电脑一样工作，实现代码、Codex 对话和工作状态的实时同步。

---

# 一、项目定位与设计目标

## 1.1 核心设计理念

澜汐不是传统的文件传输软件，也不是 Git 客户端或远程桌面软件。

它的核心目标是：

用户在电脑 A 上进行开发，完成代码修改、Codex 对话和任务操作后，切换到电脑 B，可以直接接续之前的工作。

用户不需要手动上传代码、Git Push、Git Pull，也不需要重新向 Codex 解释项目背景。

澜汐通过中心服务器协调多台设备，实现开发工作状态的连续性。

核心同步对象：

1. **代码工作区（Workspace）：** 源代码、项目文件、未提交修改、文件结构。
2. **Codex 会话（Conversation）：** 用户消息、模型回复、工具调用、审批记录、会话历史。
3. **工作状态（Runtime State）：** 当前工作设备、会话状态、任务进度、同步状态和设备交接信息。

## 1.2 核心设计原则

- 实时同步优先于传统版本管理。
- 服务器是多设备之间的同步协调中心。
- 本机负责代码编辑和 Codex 实际执行。
- 文件内容通过 HTTP 传输，WebSocket 负责实时事件通知。
- 所有同步事件必须持久化，不能只依赖内存消息。
- 断网后能够恢复，不能因为网络中断丢失本地修改。
- 不允许静默覆盖代码。
- GitHub 与澜汐实时同步系统相互独立。
- 第一阶段不引入额外云存储，所有同步文件保存在 ECS 本地磁盘。

## 1.3 第一阶段非目标

暂时不实现：

- 多人同时编辑同一个代码文件。
- 远程桌面和屏幕流传输。
- 同步完整 Python 虚拟环境、Node Modules 等依赖目录。
- 将电脑 A 上运行的任意进程直接迁移到电脑 B。
- 复杂的微服务集群。
- Kafka、Kubernetes 等大型基础设施。

```text
                  澜汐桌面客户端
              Tauri 2 + Vue 3
                       |
                       |
                 Rust Local Core
                       |
        +--------------+--------------+
        |              |              |

                       |

        |              |              |
        +--------------+--------------+

                       |
        +--------------+--------------+
        |                             |
```

整体分为三个层次：

### 客户端层

每台电脑都运行独立的澜汐客户端。

负责：

- 监听本机项目文件变化。
- 管理本机 Codex App Server。
- 收集 Codex 对话事件。
- 上传文件变化。
- 接收服务器同步事件。
- 将其他设备的文件变化应用到本机。
- 管理设备交接。

### 服务端层

Go 服务端负责：

- 设备注册和认证。
- 工作区管理。
- 文件版本管理。
- 实时事件分发。
- Codex 对话记录同步。
- 设备在线状态。
- 工作区写入权限。
- 同步进度和事件确认。

### 数据存储层

PostgreSQL 保存元数据和事件记录。

ECS 本地磁盘保存实际文件内容。

# 四、核心模块一：代码实时同步引擎

这是澜汐最重要的模块。

## 4.1 同步模式

采用：

**文件监听 + 增量文件传输 + 事件驱动 + WebSocket 通知 + 断点恢复。**

不使用定时 Git Push/Pull 作为实时同步机制。

同步粒度以文件为单位，而不是每个键盘输入字符。

例如：

电脑 A 修改 `src/main.cpp` 并保存。

澜汐检测到文件变化后，将修改上传到服务器，再通知电脑 B 下载变化。

电脑 B 不需要重新下载整个项目。

## 4.2 文件监听

Rust 本机核心负责文件监听。

建议使用 Rust `notify` 生态实现跨平台文件系统事件监听。

监听事件：

- 文件创建。
- 文件修改。
- 文件删除。
- 文件重命名。
- 目录创建。
- 目录删除。

需要实现事件防抖：

文件修改后等待约 300～500ms，再进行一次状态检查。

原因是编辑器可能通过临时文件、连续写入、原子重命名等方式保存文件。

不能把一次文件系统通知直接视为一次完整文件修改。

建议流程：

```text
文件系统事件
      |
      v
事件防抖
      |
      v
路径检查
      |
      v
读取文件状态
      |
      v
计算 SHA-256
      |
      v
与本地同步基线比较
      |
      v
生成同步任务
```

监听器需要支持定期全量校验扫描，作为文件系统事件丢失后的恢复机制。

全量扫描不是主要同步方式。

## 4.3 文件过滤规则

默认排除：

```text
.git/
node_modules/
.venv/
venv/
__pycache__/
dist/
build/
.cache/
.idea/
.vscode/
```

还应默认排除：

- 临时文件。
- 编辑器交换文件。
- 编译缓存。
- 大型模型权重。
- 数据集。
- 系统垃圾文件。
- `.env` 等敏感文件。

过滤规则需要允许用户针对工作区单独配置。

`.git` 目录默认不参与实时文件同步，Git 提交历史继续通过 GitHub 管理。

如果未来需要同步分支和工作区 Git 状态，应通过独立的 Git 元数据机制处理，不直接实时复制正在使用的 `.git` 数据库。

## 4.4 文件哈希

使用 SHA-256 识别文件内容。

例如：

```text
main.cpp
    |
    v
SHA256(file_content)
    |
    v
比较服务器文件哈希
    |
    +---- 相同：不需要上传
    |
    +---- 不同：上传新文件内容
```

主要目的：

1. 避免重复上传相同内容。
2. 验证文件传输完整性。
3. 识别文件是否真正发生变化。
4. 为未来内容寻址存储和去重提供基础。

第一阶段以整文件增量传输为主。

对于较大的文件，再增加分块上传和断点续传，不需要一开始就开发复杂的块级差异算法。

## 4.5 文件上传

文件通过 HTTP 上传，不使用 WebSocket 传输文件内容。

推荐流程：

1. 客户端计算 SHA-256。
2. 请求服务器检查目标文件当前版本。
3. 如果服务器已经有相同内容，直接跳过上传。
4. 如果不存在，上传文件到服务器临时目录。
5. 服务器验证文件大小和 SHA-256。
6. 将文件原子替换到正式工作区。
7. 更新 PostgreSQL 文件元数据。
8. 生成新的同步事件。
9. 通过 WebSocket 通知其他设备。

临时上传目录与正式文件目录必须分离。

上传完成后才能提交文件版本，避免其他设备读取到不完整文件。

## 4.6 文件下载

接收端收到 WebSocket 通知后：

1. 查询服务器当前工作区事件序号。
2. 获取自己遗漏的事件。
3. 获取变化文件的元数据。
4. 下载变化文件。
5. 验证 SHA-256。
6. 写入本地临时文件。
7. 原子重命名替换正式文件。
8. 更新本地 SQLite 同步游标。
9. 返回 ACK。

禁止直接覆盖尚未完成下载的目标文件。

# 五、核心模块二：同步事件系统

实时同步不能只依赖 WebSocket。

WebSocket 可能断线、重连、丢失连接期间的消息。

因此需要设计持久化事件系统。

## 5.1 事件模型

每个工作区拥有独立的递增事件序号。

例如：

```json
{
  "event_id": "uuid",
  "workspace_id": "workspace_001",
  "seq": 1842,
  "device_id": "device_A",
  "event_type": "file.updated",
  "path": "src/main.cpp",
  "base_version": 7,
  "new_version": 8,
  "sha256": "file_hash",
  "size": 12345,
  "timestamp": 1795350000
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| event_id | 全局唯一事件 ID |
| workspace_id | 工作区 ID |
| seq | 工作区递增序号 |
| device_id | 事件来源设备 |
| event_type | 文件操作类型 |
| path | 相对文件路径 |
| base_version | 修改前版本 |
| new_version | 修改后版本 |
| sha256 | 文件内容哈希 |
| size | 文件大小 |
| timestamp | 创建时间 |

事件类型：

```text
file.created
file.updated
file.deleted
file.renamed

workspace.snapshot
workspace.handoff

conversation.created
conversation.updated
conversation.item.created
conversation.item.updated

approval.requested
approval.resolved

device.online
device.offline
```

## 5.2 WebSocket 与 HTTP 分工

WebSocket：

- 通知文件发生变化。
- 通知会话发生变化。
- 通知审批请求。
- 通知设备上线和离线。
- 通知同步进度。

HTTP：

- 上传文件。
- 下载文件。
- 获取工作区 Manifest。
- 拉取遗漏事件。
- 提交事件确认。
- 获取 Codex 对话历史。

WebSocket 只负责通知，真正的数据通过 HTTP 获取。

这样即使 WebSocket 断开，也可以根据事件序号恢复。

## 5.3 ACK 机制

每台设备保存自己的最后确认序号。

例如：

```text
服务器当前序号：1842

电脑 A：
last_ack_seq = 1842

电脑 B：
last_ack_seq = 1838
```

电脑 B 重新连接后：

```text
GET /events?after_seq=1838
```

服务器返回 1839～1842 的事件。

电脑 B 完成文件应用后：

```text
POST /ack
{
  "workspace_id": "workspace_001",
  "last_ack_seq": 1842
}
```

服务器记录确认状态。

注意：

ACK 必须在本地数据真正应用并持久化之后提交。

事件投递采用至少一次语义。

重复收到的事件必须可以幂等处理，不能因为重复通知而重复执行文件操作。

# 六、核心模块三：多设备一致性与冲突处理

这是实时同步系统最重要的可靠性问题之一。

## 6.1 单写入者模型

第一阶段采用：

**一个工作区，同一时刻只允许一台设备拥有写入租约。**

其他设备可以查看同步状态，但默认不同时修改同一个工作区。

例如：

```text
workspace_001

电脑 A：ACTIVE_WRITER
电脑 B：READ_ONLY
手机：OBSERVER
```

这样能够大幅降低冲突发生概率。

## 6.2 工作区租约

服务器保存：

- workspace_id
- active_device_id
- lease_id
- fencing_token
- expires_at

设备需要定期续租。

建议初始心跳间隔 5 秒，租约有效期 30 秒，后续通过测试调整。

每次设备接管工作区，服务器递增 fencing_token。

旧设备即使网络恢复，也不能使用旧 token 提交新的同步事件。

需要特别注意：本地 Codex 仍可能在失去网络后继续修改文件，因此租约失效不等于本机进程自动停止。强制接管必须执行冲突检查，不能只靠服务器租约保证文件绝对不会分叉。

## 6.3 冲突处理

如果检测到：

- 两台设备同时修改同一个文件。
- 本地文件与服务器基线不一致。
- 设备离线期间产生了修改。
- 文件版本不符合预期。

禁止直接覆盖。

推荐处理：

1. 保留双方文件。
2. 生成冲突副本。
3. 标记冲突文件。
4. 通知用户。
5. 用户选择保留、合并或覆盖。

示例：

```text
main.cpp
main.conflict-device-A.cpp
```

后续可以增加可视化 Diff 合并功能。

第一阶段不实现多人实时协同编辑。

# 七、核心模块四：Codex 会话同步

代码同步和 Codex 会话同步必须是两个独立模块。

## 7.1 CodexAdapter

Rust 本机核心通过 Codex App Server JSON-RPC 管理本机 Codex。

负责：

- 获取会话列表。
- 获取会话历史。
- 监听新消息。
- 监听 Turn 状态变化。
- 监听工具调用。
- 监听审批请求。
- 记录执行结果。

不要直接把 Codex 内部数据库文件作为多设备共享数据库。

应该通过 JSON-RPC 获取数据，再转换成澜汐自己的统一会话模型。

## 7.2 会话数据结构

建议保存：

```text
Conversation
  |
  +-- Thread
        |
        +-- Turn
              |
              +-- User Message
              |
              +-- Assistant Message
              |
              +-- Tool Call
              |
              +-- Tool Result
              |
              +-- Approval
              |
              +-- Turn Status
```

PostgreSQL 保存：

- thread_id
- turn_id
- item_id
- role
- content
- item_type
- status
- sequence
- raw_event
- timestamp

原始 JSON-RPC 事件建议保留，方便未来兼容 Codex 协议变化。

## 7.3 会话同步流程

```text
电脑 A 的 Codex
       |
       v
Codex App Server
       |
       v
Rust CodexAdapter
       |
       v
本地 SQLite Outbox
       |
       v
Go Server
       |
       v
PostgreSQL
       |
       v
WebSocket 通知
       |
       v
电脑 B 的澜汐
       |
       v
更新会话界面
```

对话记录必须保留事件顺序。

工具调用和工具执行结果不能丢失，否则会造成上下文显示不完整。

## 7.4 原生会话恢复

必须区分两个能力：

**会话镜像：** 在其他电脑查看完整的 Codex 历史记录。

**原生会话恢复：** 在其他电脑恢复原来的 Codex Thread，并继续对话。

两者不是同一件事。

第一阶段先实现会话镜像。

第二阶段验证 Codex App Server 的 `thread/resume`、会话持久化数据和跨机器恢复能力。

不能直接假设复制 thread_id 和聊天记录就可以恢复原来的执行上下文。

如果原生会话迁移不受稳定接口支持，则需要提供会话接续机制：将原对话、项目状态和最近任务摘要整理成上下文，在目标设备上创建新会话继续工作。

工具调用结果只能作为历史记录展示，不允许因为同步而重复执行。

# 八、核心模块五：Workspace Handoff

这是澜汐实现无缝切换的关键模块。

## 8.1 交接流程

例如从公司电脑切换到家里电脑：

```text
电脑 A
   |
   v
暂停新的工作区写入
   |
   v
等待待上传文件完成
   |
   v
同步最新 Codex 事件
   |
   v
生成工作区快照
   |
   v
释放写入租约
   |
   v
服务器确认交接完成
   |
   v
电脑 B 获取写入租约
   |
   v
拉取遗漏事件
   |
   v
验证文件 Manifest
   |
   v
恢复工作状态
```

## 8.2 交接状态机

```text
ACTIVE
  |
  v
QUIESCING
  |
  v
SYNCING
  |
  v
SNAPSHOT_COMMITTED
  |
  v
LEASE_RELEASED
  |
  v
TARGET_ACQUIRED
  |
  v
RECONCILING
  |
  v
ACTIVE
```

每次交接生成唯一 handoff_id。

服务器记录交接前后的设备 ID、工作区版本、事件序号和状态。

如果交接中途失败，允许重新尝试，不应造成工作区锁死。

## 8.3 执行状态限制

需要明确：

- 代码可以同步。
- Codex 对话可以同步。
- 工具调用历史可以同步。
- 任务状态可以同步。
- 电脑 A 正在运行的终端进程不能直接迁移到电脑 B。
- 未保存的编辑器缓冲区默认不能同步。

如果需要真正无缝的运行环境迁移，后续需要单独研究远程工作区方案。

# 九、ECS 本地文件存储设计

不购买 OSS。

所有工作区文件直接保存在阿里云 ECS 系统盘。

建议目录：

```text
/srv/lanxi/
│
├── workspaces/
│   ├── workspace_001/
│   │   ├── files/
│   │   └── metadata/
│   │
│   ├── workspace_002/
│   │   ├── files/
│   │   └── metadata/
│
├── staging/
│
├── snapshots/
│
├── backups/
│
└── logs/
```

PostgreSQL 数据目录由系统数据库服务单独管理。

现有直接上传到 ECS 的个人项目目录作为初始数据源。

首次接入流程：

1. 确认已有项目目录。
2. 计算项目文件清单。
3. 计算 SHA-256。
4. 建立初始 Manifest。
5. 记录工作区初始版本。
6. 将现有电脑与工作区绑定。
7. 后续只同步变化。

初次导入不应盲目移动、覆盖或重新上传现有代码。

先验证现有服务器文件与本机项目是否一致。

# 十二、同步可靠性设计

必须实现以下机制：

| 机制 | 作用 |
|---|---|
| SHA-256 | 文件完整性校验 |
| Debounce | 防止文件事件过于频繁 |
| Local Outbox | 本机离线任务持久化 |
| Event Sequence | 事件排序 |
| ACK | 设备同步确认 |
| Idempotency Key | 防止重复执行 |
| Atomic Write | 防止文件写入不完整 |
| Exponential Backoff | 网络失败后重试 |
| Snapshot | 快速恢复工作区 |
| Reconciliation | 对账和差异恢复 |

重要原则：

WebSocket 断开不能影响同步数据的可靠性。

客户端重新连接后，首先比较自己的最后确认序号和服务器最新序号，再决定补拉哪些事件。

如果事件历史已经被清理，则通过最新 Manifest 重新对账。

文件应用失败时，不能提前提交 ACK。

# 十三、服务器资源与部署

当前 ECS：

- 2 vCPU 共享型。
- 2 GiB 内存。
- 40 GiB 系统盘。
- 约 28 GiB 可用空间。

第一阶段部署：

```text
Alibaba Cloud Linux 3
       |
       +-- Caddy
       |
       +-- Go Server
       |
       +-- PostgreSQL
       |
       +-- Local File Storage
```

使用 systemd 管理服务。

不部署 Redis、NATS、Kafka、MinIO 和 Kubernetes。

建议初始 PostgreSQL 参数：

| 参数 | 起始值 |
|---|---:|
| shared_buffers | 128 MB |
| max_connections | 20 |
| work_mem | 2 MB |
| maintenance_work_mem | 64 MB |

Go 数据库连接池建议初始限制在 5～10 个连接。

实际资源使用通过监控调整。

存储策略：

- 项目文件和同步数据设定配额。
- 初期建议先规划约 15 GiB 的工作区存储预算，确认现有项目体积后再调整。
- 保留至少 8 GiB 空间用于系统、数据库、临时上传、日志和运行余量。
- 临时上传文件设置超时清理。
- 日志必须轮转。
- 定期清理过期快照。

由于不使用 OSS，ECS 系统盘就是主要数据存储。必须意识到单块系统盘故障的风险，建议让客户端保留本地副本，并定期将数据库备份导出到受控的其他设备。服务器本机备份不能替代异地备份。

# 十四、安全设计

1. 所有外部通信使用 HTTPS/WSS。
2. 数据库只允许本机访问。
3. 每台设备拥有独立设备身份。
4. 每个请求校验用户、租户和工作区权限。
5. 设备密钥存放在操作系统安全存储中。
6. 审批请求绑定设备、会话、请求 ID 和过期时间。
7. Codex App Server 不暴露公网。
8. 默认排除 `.env`、私钥、访问令牌等敏感文件。
9. 路径必须限制在工作区根目录内，防止路径穿越。
10. 服务器日志不得记录访问令牌和敏感对话内容。

# 十七、最终技术选型总结

| 层级 | 技术 |
|---|---|
| UI | Vue 3 |
| 桌面容器 | Tauri 2 |
| 本机核心 | Rust + Tokio |
| 文件监听 | Rust notify |
| 本机数据库 | SQLite |
| Codex 接口 | JSON-RPC |
| 云端后端 | Go + Chi |
| 服务端数据库 | PostgreSQL |
| 文件存储 | ECS 本地文件系统 |
| 实时通信 | WebSocket |
| 文件传输 | HTTP |
| HTTPS | Caddy |
| 部署 | systemd |

**最终设计原则：**

澜汐的服务器负责保存最新的已同步工作区状态，设备负责本地工作和执行，Rust 同步引擎负责文件变化检测与应用，Go 服务端负责事件协调和多设备一致性。

GitHub 继续承担 Git 版本管理，不参与日常实时同步。

整个项目最核心的技术资产不是 UI，也不是 API，而是：

1. Rust Workspace Sync Engine。
2. Codex Conversation Adapter。
3. Go Sync Coordinator。
4. Workspace Handoff State Machine。

这四个模块决定澜汐能否真正实现多台电脑像一台电脑一样连续工作。

**第一阶段只聚焦一件事：两台电脑之间，代码修改能够可靠、实时、自动同步。**
