# 一、项目定位与设计目标

## 1.1 核心设计理念

澜汐不是传统的文件传输软件，也不是 Git 客户端或远程桌面软件。

它的核心目标是：

用户在电脑 A 上进行开发，完成代码修改、Codex 对话和任务操作后，切换到电脑 B，可以直接接续之前的工作。

用户不需要手动上传代码、Git Push、Git Pull，也不需要重新向 Codex 解释项目背景。

澜汐通过中心服务器协调多台设备，实现开发工作状态的连续性。

核心同步对象：

1. **代码工作区（Workspace）：** 源代码、项目文件、未提交修改、文件结构。
2. **Codex 会话（Conversation）：** 用户消息、模型回复、工具调用、审批记录、会话历史。
3. **工作状态（Runtime State）：** 当前工作设备、会话状态、任务进度、同步状态和设备交接信息。

## 1.2 核心设计原则

- 实时同步优先于传统版本管理。
- 服务器是多设备之间的同步协调中心。
- 本机负责代码编辑和 Codex 实际执行。
- 文件内容通过 HTTP 传输，WebSocket 负责实时事件通知。
- 所有同步事件必须持久化，不能只依赖内存消息。
- 断网后能够恢复，不能因为网络中断丢失本地修改。
- 不允许静默覆盖代码。
- GitHub 与澜汐实时同步系统相互独立。
- 第一阶段不引入额外云存储，所有同步文件保存在 ECS 本地磁盘。

## 1.3 第一阶段非目标

暂时不实现：

- 多人同时编辑同一个代码文件。
- 远程桌面和屏幕流传输。
- 同步完整 Python 虚拟环境、Node Modules 等依赖目录。
- 将电脑 A 上运行的任意进程直接迁移到电脑 B。
- 复杂的微服务集群。
- Kafka、Kubernetes 等大型基础设施。

# 三、整体系统架构

```text
                  澜汐桌面客户端
              Tauri 2 + Vue 3
                       |
                       |
                 Rust Local Core
                       |
        +--------------+--------------+
        |              |              |
   Workspace       Codex Adapter   Handoff
   Sync Engine       JSON-RPC      Manager
        |              |              |
        +--------------+--------------+
                       |
                  Local SQLite
                       |
                 HTTPS / WebSocket
                       |
              阿里云 ECS 同步中心
                       |
                Go + Chi Server
                       |
        +--------------+--------------+
        |              |              |
   Workspace       Conversation    Device
    Service          Service       Service
        |              |              |
        +--------------+--------------+
                       |
              PostgreSQL + Disk
                       |
        +--------------+--------------+
        |                             |
   工作区文件存储                  会话和事件存储
   ECS Local Disk                 PostgreSQL
```

整体分为三个层次：

### 客户端层

每台电脑都运行独立的澜汐客户端。

负责：

- 监听本机项目文件变化。
- 管理本机 Codex App Server。
- 收集 Codex 对话事件。
- 上传文件变化。
- 接收服务器同步事件。
- 将其他设备的文件变化应用到本机。
- 管理设备交接。

### 服务端层

Go 服务端负责：

- 设备注册和认证。
- 工作区管理。
- 文件版本管理。
- 实时事件分发。
- Codex 对话记录同步。
- 设备在线状态。
- 工作区写入权限。
- 同步进度和事件确认。

### 数据存储层

PostgreSQL 保存元数据和事件记录。

ECS 本地磁盘保存实际文件内容。

# 四、核心模块一：代码实时同步引擎

这是澜汐最重要的模块。

## 4.1 同步模式与本地响应

文件按保存后的内容同步。文件监听器把变化登记到本机 SQLite，上传和接收端下载由项目策略调度。GitHub 继续管理提交和分支。

| 本机项目策略 | 自动传输时机 |
|---|---|
| 高优先级 | 在线时优先处理已保存变化。小文件 1～2 秒的目标适用于收发两端都启用实时处理的项目。 |
| 每 12 小时 / 每 24 小时 | 从上次成功同步起计时，到期合并处理积累的变化。 |
| 进入后同步 | 打开本机项目先显示本地信息与会话，约 5 秒后安排后台同步，连续点击合并。 |

沿用 R51 的项目分组、每台设备的策略设置和主动进入项目后的后台刷新。手动「合流」或交接可立即调度传输，仍要校验分支和写入权。低优先级项目收到文件通知时只记录待处理序号。审批通知独立投递。[现版项目分组与同步](../../docs/PERSONAL_SYNC.md#项目分组与同步优先级)

打开已有项目只读本机数据。用户按 Enter 后，前端立即显示带稳定消息 ID 的气泡，后台把消息及发送状态写入本机队列，持久化成功后才交给发送器。落盘失败时保留文本并提示。重连后按同一 ID 合并本地气泡与服务端回执。确认尚未投递的消息可以重发。已交给 Codex 但结果未知的消息显示「结果未确认」，先核对原线程，避免重复执行。[现版即时发送与重连](../../docs/跨设备开发工作台方案.html#current)

## 4.2 文件监听

Rust 本机核心负责文件监听。

建议使用 Rust `notify` 生态实现跨平台文件系统事件监听。

监听事件：

- 文件创建。
- 文件修改。
- 文件删除。
- 文件重命名。
- 目录创建。
- 目录删除。

需要实现事件防抖：

文件修改后等待约 300～500ms，再进行一次状态检查。

原因是编辑器可能通过临时文件、连续写入、原子重命名等方式保存文件。

不能把一次文件系统通知直接视为一次完整文件修改。

建议流程：

```text
文件系统事件
      |
      v
事件防抖
      |
      v
路径检查
      |
      v
读取文件状态
      |
      v
计算 SHA-256
      |
      v
与本地同步基线比较
      |
      v
生成同步任务
```

监听器需要支持定期全量校验扫描，作为文件系统事件丢失后的恢复机制。

全量扫描不是主要同步方式。

## 4.3 文件过滤规则

默认排除：

```text
.git/
node_modules/
.venv/
venv/
__pycache__/
dist/
build/
.cache/
.idea/
.vscode/
```

还应默认排除：

- 临时文件。
- 编辑器交换文件。
- 编译缓存。
- 大型模型权重。
- 数据集。
- 系统垃圾文件。
- `.env` 等敏感文件。

过滤规则需要允许用户针对工作区单独配置。

`.git` 目录默认不参与实时文件同步，Git 提交历史继续通过 GitHub 管理。

Git 项目绑定仓库标识和登记分支，本地基线同时记录最近核对的 HEAD。扫描、生成任务和实际收发前复核分支与 Git 状态。遇到切分支、合并、变基或未解决冲突，暂停该工作区的发布及远端文件应用。回到登记分支且 Git 操作结束后，重新扫描并与同步基线对账，只提交复核过的变化。来源不明的批量增删保留现场。不同分支分别建立工作区后才能独立同步。[现版分支规则](../../docs/PERSONAL_SYNC.md#项目目录与分支)

## 4.4 文件哈希

使用 SHA-256 识别文件内容。

例如：

```text
main.cpp
    |
    v
SHA256(file_content)
    |
    v
比较服务器文件哈希
    |
    +---- 相同：不需要上传
    |
    +---- 不同：上传新文件内容
```

主要目的：

1. 避免重复上传相同内容。
2. 验证文件传输完整性。
3. 识别文件是否真正发生变化。
4. 按内容哈希保存不可变对象，供版本下载和安全重试复用。

第一阶段以整文件增量传输为主。

对于较大的文件，再增加分块上传和断点续传，不需要一开始就开发复杂的块级差异算法。

## 4.5 文件上传与版本提交

1. 客户端将本次变化的工作区、分支、相对路径、操作、基线版本和 `operation_id` 持久化。修改或新增还要固定这次上传的文件内容、大小与 SHA-256。
2. 服务器校验工作区权限和配额。对象缺失时，写入临时文件、核对长度和哈希，再在同一文件系统持久化为按哈希命名的不可变对象。相同内容可以复用。路径新增、重命名和删除仍须提交各自的操作。
3. Go 服务在单个 PostgreSQL 事务内锁定该工作区的写入状态行。获取、续签、转移租约与提交文件共用这把行锁。提交时校验登记分支、写入设备、未过期租约、`fencing_token`、各受影响路径的基线版本和对象就绪状态。在锁内分配文件事件序号，一并更新路径版本、Manifest、事件和操作回执，提交后对读者可见。
4. 事务提交后才推送 WebSocket 通知。相同工作区和操作 ID 的同一请求重试返回原回执，不再递增版本。相同 ID 携带不同内容时拒绝。过期写入权或基线冲突均保留本机任务供对账。

Manifest 是读者获取当前版本的依据。对象落盘后事务失败，只留下未引用对象，按第十三章回收。事务成功但通知或响应丢失时，客户端分别通过事件补拉或原操作 ID 找回结果。

## 4.6 下载、应用与恢复

1. 按本机文件游标补拉事件。按事件所列的工作区、路径版本和哈希读取不可变内容，校验大小和 SHA-256。历史内容已过期时转入第十二章的快照对账。
2. 接收端在 SQLite 写入应用记录，包含事件 ID、预期基线和目标状态。比较本机文件与上次已应用的基线，包括文件存在性、哈希和待上传的本地修改。重命名同时检查源、目标两条路径。遇到本地分叉时，保存本地内容和远端版本或删除记录，按第六章登记冲突。
3. 对干净路径，用目标目录同卷临时文件完成替换。替换或删除前保留可恢复的原件，复核实际移出的原件与基线一致，遇到编辑器并发写入、占用或目标路径碰撞时保留现场。重命名用同一应用记录恢复两条路径。仅在核对落盘结果后，才在 SQLite 同一事务提交路径基线、事件结果和连续游标。
4. 进程重启先恢复未完成的应用记录。文件已处于目标版本时可补记结果，仍在原基线时可重试，遇第三种内容时转为冲突。冲突两侧与记录持久化后可以确认收件，界面仍显示待解决。任何一侧未保存、写盘失败或事件缺失时，游标停在最后一个已完整处理的事件。最后向服务器发送 ACK。

# 五、核心模块二：同步事件系统

实时同步不能只依赖 WebSocket。

WebSocket 可能断线、重连、丢失连接期间的消息。

因此需要设计持久化事件系统。

## 5.1 事件模型

事件按工作区和事件流排序。`files` 记录文件变化，`conversations` 记录会话历史和删除，`control` 记录审批与交接。每条流有独立的连续序号和设备游标，序号随事务提交对读者可见。低优先级文件积压时，审批仍可送达。以下是一次文件修改事件。

```json
{
  "event_id": "uuid",
  "workspace_id": "workspace_001",
  "stream": "files",
  "seq": 1842,
  "device_id": "device_A",
  "event_type": "file.updated",
  "path": "src/main.cpp",
  "base_version": 7,
  "new_version": 8,
  "sha256": "file_hash",
  "size": 12345,
  "timestamp": 1795350000
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| event_id | 全局唯一事件 ID |
| workspace_id | 工作区 ID |
| stream | 事件流名称 |
| seq | 工作区内该事件流的提交序号 |
| device_id | 事件来源设备 |
| event_type | 文件操作类型 |
| path | 相对文件路径 |
| base_version | 修改前版本 |
| new_version | 修改后版本 |
| sha256 | 文件内容哈希 |
| size | 文件大小 |
| timestamp | 创建时间 |

删除事件携带路径、预期版本和新版本，并保留删除标记。重命名事件携带源路径、目标路径及各自的预期和提交后版本，在同一事务内登记源路径删除及目标路径变化。

事件类型：

```text
file.created
file.updated
file.deleted
file.renamed

workspace.snapshot
workspace.handoff

conversation.created
conversation.updated
conversation.deleted
conversation.item.created
conversation.item.updated

approval.requested
approval.resolved

device.online
device.offline
```

## 5.2 WebSocket 与 HTTP 分工

WebSocket：

- 通知文件发生变化。
- 通知会话发生变化。
- 通知审批请求。
- 通知设备上线和离线。
- 通知同步进度。

HTTP：

- 上传文件。
- 下载文件。
- 获取工作区 Manifest。
- 拉取遗漏事件。
- 提交事件确认。
- 获取 Codex 对话历史。

WebSocket 只负责通知，真正的数据通过 HTTP 获取。

这样即使 WebSocket 断开，也可以根据事件序号恢复。

## 5.3 ACK 机制

每台设备按工作区和事件流持久化最后连续确认的序号。以下示例为同一工作区的文件流。

例如：

```text
服务器当前序号：1842

电脑 A：
last_ack_seq = 1842

电脑 B：
last_ack_seq = 1838
```

电脑 B 重新连接后：

```text
GET /api/v1/workspaces/workspace_001/events?stream=files&after_seq=1838
```

服务器返回 1839～1842 的事件。

电脑 B 完成文件应用后：

```text
POST /api/v1/workspaces/workspace_001/ack
{
  "stream": "files",
  "last_ack_seq": 1842
}
```

服务器按已认证设备、工作区和事件流单调更新游标。客户端收到乱序通知先补齐较早事件，重复 ACK 可安全重发。

注意：

ACK 必须在本地数据真正应用并持久化之后提交。

事件投递采用至少一次语义。

重复收到的事件必须可以幂等处理，不能因为重复通知而重复执行文件操作。

# 六、核心模块三：多设备一致性与冲突处理

这是实时同步系统最重要的可靠性问题之一。

## 6.1 单写入者模型

第一阶段采用：

**一个工作区，同一时刻只允许一台设备拥有写入租约。**

其他设备可以查看同步状态，但默认不同时修改同一个工作区。

例如：

```text
workspace_001

电脑 A：ACTIVE_WRITER
电脑 B：READ_ONLY
手机：OBSERVER
```

这样能够大幅降低冲突发生概率。

## 6.2 工作区租约

服务器保存：

- workspace_id
- active_device_id
- lease_id
- fencing_token
- expires_at

设备需要定期续租。

建议初始心跳间隔 5 秒，租约有效期 30 秒，后续通过测试调整。

每次设备接管工作区，服务器递增 fencing_token。

旧设备即使网络恢复，也不能使用旧 token 提交新的同步事件。

需要特别注意：本地 Codex 仍可能在失去网络后继续修改文件，因此租约失效不等于本机进程自动停止。强制接管必须执行冲突检查，不能只靠服务器租约保证文件绝对不会分叉。

## 6.3 冲突处理

如果检测到：

- 两台设备同时修改同一个文件。
- 本地文件与服务器基线不一致。
- 设备离线期间产生了修改。
- 文件版本不符合预期。

禁止直接覆盖。

冲突副本以工作区、路径和事件 ID 唯一标识，排除在自动上传之外。远端删除记录与本机修改同样构成冲突。用户可查看双方内容，选择保留、合并或接受删除。解决后以最新远端基线和新的操作 ID 提交，期间远端再次变化则重新核对。

示例：

```text
main.cpp
main.conflict-device-A.cpp
```

后续可以增加可视化 Diff 合并功能。

第一阶段不实现多人实时协同编辑。

# 七、核心模块四：Codex 会话同步

代码同步和 Codex 会话同步必须是两个独立模块。

## 7.1 CodexAdapter

Rust 本机核心通过 Codex App Server JSON-RPC 管理本机 Codex。

负责：

- 获取会话列表。
- 获取会话历史。
- 监听新消息。
- 监听 Turn 状态变化。
- 监听工具调用。
- 监听审批请求。
- 记录执行结果。

不要直接把 Codex 内部数据库文件作为多设备共享数据库。

应该通过 JSON-RPC 获取数据，再转换成澜汐自己的统一会话模型。

## 7.2 会话数据结构

建议保存：

```text
Conversation
  |
  +-- Thread
        |
        +-- Turn
              |
              +-- User Message
              |
              +-- Assistant Message
              |
              +-- Tool Call
              |
              +-- Tool Result
              |
              +-- Approval
              |
              +-- Turn Status
```

PostgreSQL 保存：

- thread_id
- turn_id
- item_id
- role
- content
- item_type
- status
- sequence
- 诊断采样引用（可选）
- timestamp

正常同步只保存展示、排序、恢复和审批回执所需的结构化字段。`raw_event` 默认关闭。排查协议兼容问题时，可限工作区和时段采样允许字段，在来源端剔除令牌、环境变量值及完整命令输出，再写入独立诊断区。建议试点初值为 24 小时自动到期，并纳入配额。删除会话时一并清理可归属的诊断数据。原线程交接所需的授权原生记录按第 7.4 节单独管理。

## 7.3 会话同步流程

```text
电脑 A 的 Codex
       |
       v
Codex App Server
       |
       v
Rust CodexAdapter
       |
       v
本地 SQLite Outbox
       |
       v
Go Server
       |
       v
PostgreSQL
       |
       v
WebSocket 通知
       |
       v
电脑 B 的澜汐
       |
       v
更新会话界面
```

会话事件按线程内顺序写入，按 `thread_id`、来源事件标识去重。工具结果、用户消息和审批回执关联到原轮次。接收端展示历史时不会再次调用工具。

### 摘要和跨机删除

沿用现有「压缩并删除」和拖入另一会话的操作。先保存并校验 Markdown 摘要。转入主会话时，另行确认目标线程已收到摘要。来源会话空闲、原生删除条件满足后，服务端同一事务登记 `conversation.deleted` 和会话删除标记，立即停止提供原会话，安排清理正文、原生记录、诊断数据和独占分块。删除进度保留至各设备回执。[现版摘要与跨机删除](../../docs/DESKTOP.md#压缩并删除-codex-会话)

删除标记以工作区和原线程 ID 为键，跨越事件清理和快照恢复长期保留，仅含删除标识和回执信息。服务端处理补传时首先检查标记，迟到的创建、消息或工具结果不得重建旧线程。离线设备重连先取删除标记，取消该线程的待传记录。待原生占用解除并完成本机清理后回执，重试复用同一删除 ID。

## 7.4 原生会话恢复与审批

P2 交付会话镜像。正式替换 R51 前，P3 必须在目标客户端兼容的 Codex 版本上恢复同一原生线程。试点沿用 R51 已支持的封存与恢复路径，记录原线程 ID、轮次、原生记录摘要和映射后的工作目录。目标端已有后续轮次时先检查共同前缀，分叉时保留双方。可以验证 App Server 的 `thread/resume` 作为接入方式。用户选择的摘要开新会话应单独标识。[现版原生接续](../../docs/HANDOFF.md)

澜汐托管的审批经来源 Codex 连接处理，独立终端或 VS Code 的审批沿用本机已信任的 Hook。保留「接受一次」「拒绝」及「回到 Codex」。展示的历史审批与当前待处理请求分别存储。转发决定前核对来源设备、线程、请求 ID、有效期和当前控制权，由来源端回执。重复决定复用回执，来源端结果未知时先核对请求状态。重连、旧快照和历史回放均不能触发二次批准或重复弹窗。[现版审批与托盘行为](../../docs/跨设备开发工作台方案.html#current)

# 八、核心模块五：Workspace Handoff

这是澜汐实现无缝切换的关键模块。

## 8.1 交接流程

例如从公司电脑切换到家里电脑：

```text
电脑 A
   |
   v
暂停新指令，等待在途轮次和审批有确定结果
   |
   v
等待待上传文件完成
   |
   v
同步最新 Codex 事件
   |
   v
持久化同一交接点的文件快照、会话检查点和审批结果
   |
   v
释放写入租约
   |
   v
服务器记录源端已交还，保留目标设备和交接点
   |
   v
电脑 B 获取写入租约
   |
   v
拉取遗漏事件
   |
   v
核对文件 Manifest、线程检查点和目标端工作目录
   |
   v
恢复原线程并确认接管，开放写入
```

## 8.2 交接状态机

```text
ACTIVE
  |
  v
QUIESCING
  |
  v
SYNCING
  |
  v
SNAPSHOT_COMMITTED
  |
  v
LEASE_RELEASED
  |
  v
TARGET_ACQUIRED
  |
  v
RECONCILING
  |
  v
ACTIVE
```

每次交接生成唯一 handoff_id。

交接记录绑定源和目标设备、登记分支及基准提交、文件快照 ID 与文件游标、原线程 ID、最后完成轮次、原生记录哈希和审批状态。源端在同一稳定状态下复查文件及原生会话，确认服务器已持久化后再交还。有在途轮次、待审批、未确认的审批结果或未保存的同步变化时，交接保持等待。缩到托盘也遵循这一流程。[现版项目交还](../../docs/PROJECT_CONTROL.md)

服务器锁定同一条交接记录完成状态推进，并核对租约代次。目标端在 `RECONCILING` 阶段只做恢复和验证，直到文件、会话和路径映射均与交接点一致才开放执行。任一步中断均凭 `handoff_id` 查询已完成步骤并重试。租约超时只撤销旧写权，不能把异常中断登记为正常交接。

## 8.3 执行状态限制

需要明确：

- 代码可以同步。
- Codex 对话可以同步。
- 工具调用历史可以同步。
- 任务状态可以同步。
- 电脑 A 正在运行的终端进程不能直接迁移到电脑 B。
- 未保存的编辑器缓冲区默认不能同步。

如果需要真正无缝的运行环境迁移，后续需要单独研究远程工作区方案。

# 九、存储布局与 R51 迁移

试点在隔离的服务实例上运行，使用独立数据库、文件根目录和设备身份。每个工作区有自己的不可变内容对象和临时上传目录，二者位于同一文件系统。PostgreSQL 保存版本、清单、游标与回执。快照由固定序号的清单及其引用的对象组成。旧服务的数据卷保留至回退演练结束。

| 步骤 | 项目负责人要核对的结果 |
|---|---|
| 1. 只读盘点 | 先选一个测试项目。逐项记录 R51 服务器备份 ZIP 或已有目录的来源设备、时间与哈希，GitHub 登记分支和提交，以及两端本地的暂存、未提交、未跟踪和已删除文件。服务器备份按设备生成，可能早于本机修改。[现版服务器备份](../../docs/PERSONAL_SYNC.md#代码的服务器备份) |
| 2. 确认初始基线 | 以共同提交核对已提交代码。对工作区差异，采用经核实的来源设备版本或保留冲突候选，由负责人记录选择。为初始清单记录来源、提交、路径、内容哈希和版本。服务器已有的匹配内容直接复用，仅补齐缺失对象。在隔离目录还原并比对后登记初始快照。 |
| 3. 切换一个项目 | 先冻结该项目的旧自动写入和旧客户端补传，排空并核对已接受操作。保存最后的 R51 备份、原生会话、审批结果和删除记录。复核初始清单后，在服务器按项目切换唯一写入方，拒绝旧客户端迟到的写请求。旧端仍能独立写同一项目时，试点限于隔离副本。 |
| 4. 回滚演练 | 暂停新写入，保存切换后最后一个已提交游标和两端待传数据。导出从初始快照到停写点的文件增删改、会话增量、摘要、删除标记与审批结果，按路径基线合并到隔离的 R51 恢复副本。核对内容哈希、原线程、删除状态和待传清单，审批按原回执恢复。无法无损映射的记录先留存，项目保持冻结。验证成功后才交回旧写入方。 |

试点报告保留切换与回滚前后的清单、可恢复备份位置和差异处理结果，再决定扩大项目范围。

# 十一、服务端 API 设计

建议 REST + WebSocket。

## 11.1 设备管理

```text
POST /api/v1/devices/register
GET  /api/v1/devices
POST /api/v1/devices/heartbeat
POST /api/v1/devices/offline
```

## 11.2 工作区管理

```text
POST /api/v1/workspaces
GET  /api/v1/workspaces
GET  /api/v1/workspaces/{id}
GET  /api/v1/workspaces/{id}/manifest?snapshot_id={snapshot_id}
```

首次获取可省略 `snapshot_id`，响应返回固定的快照 ID、`snapshot_seq` 和保留期限，后续各页使用同一 ID。设备对账期间可在保留期限内按清单读取对象。

## 11.3 文件同步

```text

GET  /api/v1/workspaces/{id}/objects/{sha256}

```

对象读取按工作区授权。`files/operations` 接受新增、更新、删除和重命名，统一执行第 4.5 节的权限、版本和幂等检查。期望版本冲突返回 409，写入租约失效时拒绝写入，已清理的历史对象返回 410 并引导快照对账。

## 11.4 事件同步

```text
GET  /api/v1/workspaces/{id}/events?stream=files&after_seq=100

```

```text
POST /api/v1/workspaces/{id}/lease/acquire
POST /api/v1/workspaces/{id}/lease/renew
POST /api/v1/workspaces/{id}/lease/release

```

## 11.6 Codex 会话


# 十二、同步可靠性设计

必须实现以下机制：

| 机制 | 作用 |
|---|---|
| SHA-256 | 文件完整性校验 |
| Debounce | 防止文件事件过于频繁 |
| Local Outbox | 本机离线任务持久化 |
| Event Sequence | 事件排序 |
| ACK | 设备同步确认 |
| Idempotency Key | 防止重复执行 |
| Atomic Write | 防止文件写入不完整 |
| Exponential Backoff | 网络失败后重试 |
| Snapshot | 快速恢复工作区 |
| Reconciliation | 对账和差异恢复 |

重要原则：

WebSocket 断开不能影响同步数据的可靠性。

每条流从已持久化的连续游标补拉。文件事件或所需历史对象已过期时，服务器返回 410。客户端锁定带 `snapshot_seq` 的一致清单，按第 4.6 节逐项核对本机基线、清单中新增或缺失的路径及待传任务。所有变更和冲突副本落盘后才保存快照游标，从 `snapshot_seq + 1` 接收增量。对账期间新提交的事件仍可补拉。快照过期则重新取快照，保留本地改动。

会话流或控制流出现缺口时，分别获取带本流游标的当前状态。会话恢复含删除标记，控制恢复含来源端待审批项及决策回执。各流独立确认。未完成的本地应用记录按第 4.6 节恢复。

状态快照接口见第十一章，返回的状态与对应流的序号来自同一已提交视图。

# 十三、服务器资源与部署

当前 ECS：

- 2 vCPU 共享型。
- 2 GiB 内存。
- 40 GiB 系统盘。
- 约 28 GiB 可用空间。

第一阶段部署：

```text
Alibaba Cloud Linux 3
       |
       +-- Caddy
       |
       +-- Go Server
       |
       +-- PostgreSQL
       |
       +-- Local File Storage
```

使用 systemd 管理服务。

不部署 Redis、NATS、Kafka、MinIO 和 Kubernetes。

建议初始 PostgreSQL 参数：

| 参数 | 起始值 |
|---|---:|
| shared_buffers | 128 MB |
| max_connections | 20 |
| work_mem | 2 MB |
| maintenance_work_mem | 64 MB |

Go 数据库连接池建议初始限制在 5～10 个连接。

实际资源使用通过监控调整。

### 容量预算、清理与恢复

盘点时系统盘约余 28 GiB。试点先以 15 GiB 作为工作区上限，包含当前内容、保留的历史版本和快照独占数据，同一不可变对象只计一次。预留至少 8 GiB 空闲供系统与故障恢复，余下约 5 GiB 是数据库及 WAL、在途上传、日志、诊断和本地备份暂存**合计可增长**的初步预算。并行运行 R51 也使用这块磁盘，部署前按实际空闲量缩小额度。上述数值为起始配置。

- 接收上传前按最大落盘量预留空间，约束并发和工作区总额。达到配额或空闲下限时暂停新写并提示，已提交版本仍可读取，客户端保留待传任务。
- 清理顺序为过期诊断、日志、超时的上传暂存，再处理历史版本。先解除已到期的历史和快照引用，仅回收未被当前清单、可回放事件、有效快照、正在提交的上传或回滚点引用的内容。上传转为已引用对象与回收互斥，保留期和清理水位可观测。
- 异地备份包括同一快照的数据库元数据、会话删除标记、审批回执以及引用的对象。试点用空数据目录做一次还原，核对清单哈希、线程和游标，再登记备份可用。

# 十四、安全设计

1. 所有外部通信使用 HTTPS/WSS。
2. 数据库只允许本机访问。
3. 每台设备拥有独立设备身份。
4. 每个请求校验用户、租户和工作区权限。
5. 设备密钥存放在操作系统安全存储中。
6. 审批请求绑定设备、会话、请求 ID 和过期时间。
7. Codex App Server 不暴露公网。
8. 默认排除 `.env`、私钥、访问令牌等敏感文件。
9. 路径必须限制在工作区根目录内，防止路径穿越。
10. 服务器日志不得记录访问令牌和敏感对话内容。

# 十七、最终技术选型总结

| 层级 | 技术 |
|---|---|
| UI | Vue 3 |
| 桌面容器 | Tauri 2 |
| 本机核心 | Rust + Tokio |
| 文件监听 | Rust notify |
| 本机数据库 | SQLite |
| Codex 接口 | JSON-RPC |
| 云端后端 | Go + Chi |
| 服务端数据库 | PostgreSQL |
| 文件存储 | ECS 本地文件系统 |
| 实时通信 | WebSocket |
| 文件传输 | HTTP |
| HTTPS | Caddy |
| 部署 | systemd |

**最终设计原则：**

澜汐的服务器负责保存最新的已同步工作区状态，设备负责本地工作和执行，Rust 同步引擎负责文件变化检测与应用，Go 服务端负责事件协调和多设备一致性。

GitHub 继续承担 Git 版本管理，不参与日常实时同步。

整个项目最核心的技术资产不是 UI，也不是 API，而是：

1. Rust Workspace Sync Engine。
2. Codex Conversation Adapter。
3. Go Sync Coordinator。
4. Workspace Handoff State Machine。

这四个模块决定澜汐能否真正实现多台电脑像一台电脑一样连续工作。

第一阶段先验证一个项目的代码修改可以安全往返并回滚。正式替代 R51 的条件见第十五、十六章。
